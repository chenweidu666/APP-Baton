## 1. 使用与键位（日常使用）

> **机型**：小米蓝牙语音遥控器 2 Pro（RC003）· `F0:2B:18:87:37:B7`（13 键）· 电量：`bluetoothctl info F0:2B:18:87:37:B7 | grep -i battery`
> **配置**：`~/.config/mi-remote-linux/mapping.json` ｜ **生效**：`systemctl --user restart mi-remote`（两个服务开机自启，平时不用管）

![默认键位图](images/keymap.png)


**计时约定**：短按 = 按一下；**长按 = 按住 ≥ 350ms**；**双击 = 快速按两下（间隔 < 250ms）**

### 1.3 两个「模式」

#### 1.3.1 语音输入（按住语音键）

- **按住**说话 → **松手**开始识别 → 自动粘贴到当前焦点
- **建议**：用小米 **MiMo**（`mimo-v2.5-asr`）做语音识别。本仓库默认就是这条路径；把 Token Plan 的 Key 写进本机 [`system/cloud-asr.json`](../system/cloud-asr.json)（**含 api_key，不进 git**）。本分支**不分发本地语音模型**。
- 若要换别的 OpenAI 兼容接口，只改这一份 JSON；日常仍建议留在小米 MiMo。
- 可以连续口述多句，每句松手后即上屏
- 麦克风在**遥控器上**，所以离电脑多远都能说（这是它比"用电脑麦克风"强的地方）
- 终端里粘贴走 `Ctrl+Shift+V`（服务参数 `--paste-shortcut ctrl-shift-v` 指定）

**为什么建议 MiMo，而不是本机塞一个离线模型**

| 原因 | 说明 |
|---|---|
| **识别率** | 电视遥控麦是远场、小振膜、IMA ADPCM，本身信号质量一般；小米官方把 `mimo-v2.5-asr` 写成面向中英双语、方言、**远场 / 高噪声**，和这只遥控器的使用场景对得上。（⚠️ 早期把「本草枯」这类乱码归咎于麦太热/削波，**是误诊** —— 真因见坑 14：音频通知被重复订阅，同一帧被解码 N 遍。修好后同一条麦识别正常。） |
| **效率** | 云端识别后本机不必加载约 233 MB 的 ONNX，服务内存大约几十 MB，而不是三四百 MB。松手后实测转写大约 **0.7–0.9 秒**，沙发上口述 prompt 够用。 |
| **成本** | 按**音频时长**计费，遥控器是按住说话、每句通常几秒，比「挂着一直录音」便宜一个数量级。单价见下表。 |

官方标价（以 [Token Plan 价格页](https://mimo.mi.com/docs/zh-CN/price/token-plan) 与 [mimo-v2.5-asr](https://mimo.mi.com/models/mimo-v2.5-asr) 为准，价格会变）：

| 计费方式 | 语音识别怎么扣 | 换算到遥控器 |
|---|---|---|
| **按量** | **¥0.5 / 音频小时**（约 $0.074 / 小时） | 一句 5 秒 ≈ **¥0.0007**；一天口述 100 句（共约 8 分钟音频）≈ **¥0.07** |
| **Token Plan** | `mimo-v2.5-asr`：**30M Credits / 音频小时**（按秒折算） | Lite（¥39/月、41 亿 Credits）若额度全给 ASR，官方折合约 **136.6 小时/月**（每天约 4.5 小时音频）。沙发写代码远用不完。 |

Token Plan 的 Credits 会和对话模型**共用额度**；上表「全给 ASR」只是上限，用来说明语音本身不贵。

**关于「让小米顺便整理语义」——做不到，卡在网关**

会有人想：既然小米是云端大模型，能不能在转写时顺手把口语顺成书面语？**不行**，三条路都试过（2026-10 实测）：

| 尝试 | 结果 |
|---|---|
| 在 `content` 里加 `{"type":"text", ...}` 指令 | `HTTP 400 ASR request must not include text parts; text prompt is injected by the gateway` |
| `asr_options` 里加 `prompt` / `hotwords` | 静默忽略，结果一字不变 |
| 顶层 `prompt`、`role: system`、`punctuation` / `itn` | 静默忽略，结果一字不变 |

`mimo-v2.5-asr` 是**纯转写模型**，它的提示词由小米网关在服务端注入，不对外开放。所以本仓库发出去的请求**只有音频 + 语种，没有任何提示词**（见 `system/patch/mimo_asr.py` 的请求体）——不是忘了写，是写不进去。

**语种（`language`）**：官方支持 `auto` / `zh` / `en`，**默认 `auto`**，且模型本身支持**中英双语 + 代码混说（code-switching）**。本仓库以 `system/cloud-asr.json` 的 `language` 为准，**默认 `auto`** —— **中英混说千万别选 `zh`**，否则英文会被按中文音译（实测 `Cursor → 克鲁兹`、`FFmpeg → FFMPG`）。这类专有词**不能用 ASR 热词偏置**（网关静默忽略），只能走第二层整理的 `glossary` 术语表（见下文「让第二层懂行」）。

**送云端前的音频归一化**（`normalize` 段，**默认开**）：

```json
"normalize": {
  "enabled": true,
  "target_rms_dbfs": -16,
  "peak_ceiling_dbfs": -2
}
```

- 遥控麦电平随远近/音量差异极大（实测 RMS 从 **-37 到 -3 dBFS**）；这里把每句话归一到统一的目标 RMS，并用峰值上限压掉个别尖峰（**只压尖峰，不因此把整句拉低**）。
- 实测模型本身对电平并不敏感（-37 dBFS 的轻声也能转对），所以这项是"一致性"保险，不想用可 `"enabled": false`。
- 单位是 dBFS（0 dBFS = 32768）；日志会打印 `音频归一化：x dB（RMS a→b，峰值 c→d，压峰 n 样本）` 便于核对。
- ⚠️ 日志里 `峰值 32768`（顶满）**未必是麦克风削波**：实测主因是坑 14 的「音频通知重复订阅」——同一帧被解码 N 遍会把 ADPCM 预测器推到轨上，做出又响又削的假波形。**出现持续满刻度先查坑 14，而不是先怪麦**。归一化只保证"送出去的信号电平一致、不削顶"，不能还原真正削掉的波形。

本仓库**可选**再加一道对话模型（`cleanup`，**默认关闭**）：

```
mimo-v2.5-asr（转写）──► mimo-v2.6-flash（整理）──► 上屏
```

**开关与调参**在 `system/cloud-asr.json` 的 `cleanup` 段：

```json
"cleanup": {
  "enabled": false,
  "model": "mimo-v2.6-flash",
  "timeout_seconds": 20,
  "min_chars": 0,
  "glossary": [
    { "term": "Vibe Coding", "aliases": ["Web God", "Web Calling", "Web Coding"] }
  ]
}
```

#### 让第二层「懂行」：语境 + 术语表（都发给大模型）

- **用户语境写进提示词**：默认提示词已写明「用户是程序员、日常做程序开发、口述内容基本是给 AI 编程工具的
  prompt」，遇到近音、拿不准的词**优先按开发语境理解**，而不是按日常口语猜。
- **术语表 `glossary` 也发给大模型**（关键）：网关会**静默忽略** ASR 的 `hotwords`（见上文三条实测），
  所以专有词偏置只能走第二层。`glossary` 支持两种写法：
  - `["Vibe Coding"]` —— 只给正确写法；
  - `{ "term": "Vibe Coding", "aliases": ["Web God"] }` —— `aliases` 是**实际观察到的听错形式**，作提示。
- 实测：遥控器把 **`Vibe Coding` 快读成 `Web God` / `Web Calling`**；配了这条术语表后，
  三种错法都稳定归一到 `Vibe Coding`，而 `WebSocket` 等**表外**词原样保留。
- **明确禁止凭空替换**：提示词第 5 条写死「语境不足以确定时保持转写原样，宁可不改，不许补造专有名词」，
  并且**只在真的配了 `glossary` 时**才追加「术语表优先」条款（没配表时提示词里不出现「术语表」，避免悬空引用）。
  这条是踩坑换来的：没有「不许发明」约束时，模型会把不认识的词自己编一个（实测把 `Web God` 编成 `Web Coding`）。

- **代码默认关**：不加 `cleanup` 段就是"转写即上屏"，实测约 **1 秒**（4 次：1.04 / 0.97 / 0.92 / 1.33 秒）
- 本机部署**已开**（`"enabled": true`）：上屏总耗时 = ASR ≈1 秒 + 第二道调用
- **第二道实测延迟波动很大，且本地不可控**：连打 4 次的实测分布约 **2.5 / 3.0 / 6.1 / 5.9 秒**（中位≈4.4 秒）；
  另有静置后的冷启动尖峰（曾测到 7–15 秒）。已开的提速项：`thinking` 关思考、用最快的 `mimo-v2.6-flash`；
  缩短提示词约省 1 秒；`max_completion_tokens` 调小**无效**（输出长度≈你这句话的长度，是主要成本）。剩余波动来自服务端。
- `min_chars`：短于这个字数就跳过整理（比如设 8，一句「继续」就不用多等一趟）——**追求速度就靠它**
- `model` 可换：`mimo-v2.5` 或 `mimo-v2.5-pro`（更稳但更慢）；**别换 `pro` 求快**
- 整理提示词是**保守尺度**：纠错别字、补标点、去口水词，并**可在不改变原意的前提下调整语序**；
  代码 / 命令 / 路径 / 变量名 / 技术术语原样保留，不翻译、不凭想象替换
- **任何失败都不会丢字**：超时、空结果、长度异常（相对原文过短或过长）、像拒答、像工具调用——一律**回退转写原文**

> ⚠️ **要开着整理，就得接受延迟**：第二道调用实测 **2.5–6 秒**（波动大）＋ ASR 约 1 秒；冷启动首句可达 **7–15 秒**。
> 嫌慢的三条路：① 把 `enabled` 改回 `false`；② 用 `min_chars` 让短句跳过；③ 接受它，因为整理质量确实更好。
>
> ⚠️ **整理提示词必须明确「只整理、不执行」**。实测提示词写得含糊时，模型会把你口述的 prompt 当成任务去执行（甚至吐 `tool_call`），结果是既没整理、延迟还飙到十几秒。默认提示词已写死这条约束，后处理里也会拦掉工具调用类输出。
>
> 长度守卫按输入分档：短句（<24 字）下限 0.2、长句 0.4，扩写上限 2.2。否则「嗯，那个，就是，测试一下，测试一下。」这类去完口水词只剩几个字的短句会被误判成"内容被吞"而回退原文。

#### 1.3.2 窗口切换器（长按菜单）

| 操作 | 效果 |
|---|---|
| **长按菜单**（≥350ms） | 打开 GNOME 窗口切换器，**保持 Alt 按下**，并弹通知提示 |
| **← / →** | 在所有窗口之间向前 / 向后移动选择 |
| **再长按菜单** | 前进一个窗口，**并顺延闲置计时** |
| **停止操作 8 秒** | 自动松开 Alt → 选定当前高亮的窗口 |
| 按 **Esc**（= 返回双击） | 取消切换（Alt 会在闲置计时结束后释放） |

> **为什么必须"保持 Alt"**：GNOME 每次**独立**按下 `Alt+Tab` 都会刷新 MRU 顺序，所以独立按下只能在最近两个窗口之间来回跳；**按住 Alt** 才能真正遍历所有窗口。
>
> **计时是"闲置 8 秒"**：从打开（或上次长按菜单）起算 8 秒内没有新操作才收尾 —— 期间可以慢慢按 ←/→。**想继续浏览就再长按菜单**（前进一个 + 顺延 8 秒）。到期自动松开 Alt，**Alt 不会卡住**；脚本 `trap` 也兜底释放。脚本：`~/.local/bin/window-switcher [闲置秒数]`

### 1.4 启动程序（遥控器直达 + 命令行）

**遥控器**（两步直达，不再经过"启动层"）：

| 操作 | 效果 |
|---|---|
| **双击主页** | 🚀 打开 **OpenCode**（`~/Workspace`，最大化） |
| **双击 TV** | 🖱️ 打开 **Cursor**（`~/Workspace`；首次需手动最大化一次，见下） |

**两个特性**：

1. **窗口最大化** —— OpenCode / 终端靠 `gnome-terminal --maximize` 自动最大化。
   **Cursor 不做特殊处理**：第一次打开后请**手动最大化一次**（`Super` + `↑`，或双击标题栏），Cursor 会记住该工作区的窗口状态，之后从遥控器打开就是最大化。
2. **已打开就拉到前台** —— 该目录的窗口已存在时不新开，直接切到最前（实测窗口数不变，日志写 `focus ...`）

**命令行 / 桌面图标**（终端、文件管理器、其他项目走这里）：

```bash
open-workspace-opencode [目录]   # OpenCode（默认 ~/Workspace；最大化；已开则拉前台）
open-workspace-cursor   [目录]   # Cursor（同上）
open-workspace-terminal [目录]   # 普通终端（最大化）
open-workspace-files    [目录]   # 文件管理器
```

桌面图标：应用列表搜「**OpenCode Workspace**」。触发日志：`~/.local/state/mi-remote-launch.log`（`launch` / `focus` / `switcher open`）

### 1.5 机制与时序参数

| 项目 | 值 | 说明 |
|---|---|---|
| 层 | 目前只剩项目自带的**孤儿层 1/2/3**（无入口，不影响使用） |
| 逃生舱 | **长按菜单 1.5 秒** | 任何层里强制回基础层（350ms 会先开切换器，1.5 秒才触发逃生舱） |
| 长按判定 | **350 ms** | `settings.hold_ms` |
| 双击判定窗口 | **250 ms** | `settings.double_ms` |
| 层空闲超时 | **20 秒** | `settings.layer_idle_ms` |
| 切换器收尾 | **闲置 8 秒** | `window-switcher` 参数（再长按菜单可顺延） |

> 遥控器是**单键 rollover**（按不出组合键），所以本表所有"组合"都是**序列**（双击、进层再按），不是同时按多个键。

### 1.10 排障对照表与已知限制

| 现象 | 原因 / 解决 |
|---|---|
| 短按有约 250ms 延迟 | 只有**主页 / TV** 还带双击判定；`settings.double_ms` 可调到 180。**返回 / 菜单 / 电源都已去掉双击 → 短按即时**（Esc、删除都不再等） |
| 不小心把窗口关掉了 | 关闭窗口现在是**长按电源**（`Alt+F4`），且**双击已移除** —— 连按两次电源只会发两次 `Esc`，不会误关窗口 |
| 想恢复"关显示器 / 鼠标模式" | 现在电源给了 Esc 与关窗；想换回：`power.tap` = `{"type":"system","value":"display_sleep"}`（关显示器）、`power.hold` = `{"type":"mouse_mode"}`（鼠标模式） |
| 主页短按 / 长按没反应 | 已按需求去掉（原 `Ctrl+G` / `Ctrl+Alt+G`）；主页只保留**双击启动 OpenCode** |
| 想看所有窗口缩略图（原来长按 TV） | 长按 TV 的活动概览已按需求去掉；改用**长按菜单**的窗口切换器（`←/→` 遍历所有窗口），或用 `Super`+`↑` 让某个窗口最大化 |
| 想删字又怕误触 Esc | 现在**返回短按就是删除**（即时、连按只删），`Esc` 挪到**电源短按**，两者不会互相干扰 |
| 删着删着把 AI 打断了 | 老问题：连按返回曾被双击判定吞掉变成 `Esc`。现**已去掉返回的双击**、`Esc` 改到**电源短按**，连按返回只删不打断 |
| 长按返回不连续删除 | 基础层把「长按返回」硬编码成只发一次 `Backspace`，需要本机补丁才能改。**现已启用**：长按 ≥350ms → 连续快删约 25 个字符（见坑 9；重装 mi-remote 后要重跑补丁） |
| 想恢复已撤功能（长按连删 / 启动层 / OpenCode 层 / 鼠标模式） | 都有配置备份或实现留档，恢复方式见根目录 [`CHANGELOG.md`](../CHANGELOG.md) 的「移除」一节 |
| 双击后紧接着再按同键没反应 | 双击后约 0.5 秒是状态机收尾期（正常使用不会这么按） |
| 音量键不调音量、只翻页 | 已按需求把 `vol_up`/`vol_down` 短按改成 `PageUp`/`PageDown`（不再有音量 OSD）；想恢复见 1.9 |
| 遥控器突然不生效 | 蓝牙遥控器**同一时间只能连一个主机**；若拿去控电视，回来需按「菜单 + HOME」重新配对 |
| 语音识别结果没粘进去 | 终端里用 `Ctrl+Shift+V`（已配）；若被占用可手动粘贴，文本仍留在剪贴板 |
| 小米云端 ASR 挂了怎么知道 | 说完没字上屏；会弹「小米语音识别挂了」。也可 `cloud-asr-health` 或 `journalctl --user -u mi-remote -e` 看「云端 ASR」 |
| 语音识别乱码（「本草枯」「存学」这类），且**越用越糟** | **真因是坑 14**：音频通知被重复订阅，同帧被解码 N 遍。先 `systemctl --user restart mi-remote` 立即恢复；常驻守卫 `baton-asr-guard` 自动自愈。（早期误诊为 `--gain 6` 把遥控麦削波，故服务已改 `--gain 0`；该设置保留，但它不是主因） |
| 语音识别**越来越**不准（乱码、上屏字少） | BLE 音频通知被**重复订阅**，同帧被解码 N 遍（见坑 14）。先 `systemctl --user restart mi-remote` 立即恢复；常驻守卫 `baton-asr-guard` 会自动自愈 |
| 打开程序时是"新开窗口"而非切前台 | 检查 GNOME 扩展 `winrects@cua` 是否启用（`gnome-extensions list --enabled`）；禁用后会降级为新开窗口 |
| 新窗口没最大化 | OpenCode / 终端自动最大化（`--maximize`）；**Cursor 需手动最大化一次**（`Super`+`↑` 或双击标题栏），之后它会记住该工作区 |

| 长按菜单后 ←/→ 没反应 / 切换器已消失 | 旧的 3 秒窗口太短，现已改为**闲置 8 秒**；若仍嫌短：再长按菜单可**顺延 8 秒**，或用 `window-switcher 15` 加大并改配置里的参数 |

### 2.2 原理

#### 2.2.1 遥控器的两条独立链路

```
小米蓝牙语音遥控器
      │  蓝牙 BLE
      ├── HID 通道（按键）────► /dev/input/eventN ──► mi-remote ──► 桌面动作
      │                                              （uinput 注入 / wpctl / notify-send）
      └── ATVV 通道（麦克风）─► 音频流 ──► IMA ADPCM 解码 ──► 小米 MiMo ASR（建议）
                                                ──► 剪贴板 ──► Ctrl+Shift+V
```

1. **按键走标准 BLE HID**，Linux 直接认成键盘设备，无需驱动。
2. **麦克风走 Google 的 ATVV GATT 服务**（UUID `ab5e0001~0004`），音频为 IMA ADPCM / 16 kHz 单声道，必须由程序主动连接解码 —— **它不会自动变成系统麦克风**。
3. 因此"用讯飞/搜狗输入法的语音输入"是另一条路线（电脑麦克风），用不上遥控器自带麦。本项目走遥控器麦 + **建议用小米 MiMo 识别**，优势是**拿着遥控器离电脑多远都能说**。

#### 2.2.2 为什么 GNOME Wayland 下必须自己实现注入

| 方案 | 原理 | 本机（GNOME Wayland） | 说明 |
|---|---|---|---|
| `wtype` | `zwp_virtual_keyboard` 协议 | ❌ **Mutter 未实现** | 项目默认首选，必须卸载 |
| `xdotool` | X11 | ❌ 拿不到活动窗口 | 仅 X11 会话可用 |
| `ydotool` | uinput + 守护进程 | ⚠️ 客户端可用，**Ubuntu 包缺 `ydotoold`** | 上游依赖仓库已失效，编译不通 |
| **本文的 uinput 垫片** | uinput + unix socket | ✅ **30 ms/次** | 自写，约 250 行 |

### 2.5 键位设计要点（完整表见第 1 章）

#### 2.5.1 为什么只能改全局映射

GNOME Wayland 下项目拿不到前台应用，自带的 14 个 App profile 不会触发 → 只能做**全局**映射。

#### 2.5.2 三条设计原则

1. **遥控器是单键 rollover**（按不出组合键）→ 物理上按不出 `Ctrl+Enter`。要发组合键，用注入里的 `mods`（例如**长按 OK**），或双击 / 进层再按这类序列。
2. **一个按键最多三种手势**：短按 / 长按（≥350ms）/ 双击（<250ms 内两下）；配了双击的键，短按会有 250ms 判定延迟。
3. **常用动作放最短路径**：口述、发送、删除、切窗口、启动程序各占一个"一眼能找到"的位置。

#### 2.5.3 窗口切换器为什么「保持 Alt」

GNOME 每次**独立**按下 `Alt+Tab` 都会刷新 MRU，所以独立按下只能在最近两个窗口间跳；**按住 Alt** 才会弹出可遍历所有窗口的切换器。

因此实现的不是"按一下切一个"，而是：**长按菜单 → 按下 Alt 并保持 → 期间用 ←/→ 遍历 → 闲置 8 秒自动选定**（每次再长按菜单 = 前进一个 + 顺延计时）。见 2.6 坑 11。

#### 2.5.4 配置写法示例

```json
"home": {
  "tap":  { "type": "key_stroke", "key": "g", "mods": ["ctrl"] },
  "hold": { "type": "key_stroke", "key": "g", "mods": ["ctrl", "alt"] },
  "double": { "type": "command",
              "argv": ["/home/chenwei/.local/bin/open-workspace-opencode", "/home/chenwei/Workspace"] }
},
"back": {
  "tap":    { "type": "key_stroke", "key": "backspace" },
  "double": { "type": "key_stroke", "key": "escape" }
},
"tv": {
  "tap":  { "type": "layer_toggle", "value": 5 },
  "hold": { "type": "command", "argv": ["/home/chenwei/.local/bin/ydotool", "key", "125:1", "125:0"] }
}
```

> `125` = evdev `KEY_LEFTMETA`（Super）。因 wtype 已卸载，Super 键改用自家垫片直接注入。

#### 2.5.5 支持的动作用法

`key_stroke`（key + mods）、`text`、`command`（argv 数组，不走 shell）、`system`、`open_app`、`window_cycle`、`tab_jump`、`focus_input`、`mouse_mode`、`overlay`、`voice`、`layer_momentary`、`layer_toggle`、`macro`（steps + delay）、`none`。
每个按键支持 `tap` / `hold` / `double` / `gesture` / `layers`；换固件不同的遥控器时，用 `keys watch` 取真实码值并在根级 `key_codes` 覆盖（如 `{"200":"voice"}`）。

### 2.6 踩坑记录（14 条）

#### 2.6.1 坑 1：项目自带的 udev 规则在蓝牙遥控器上失效

- **现象**：装完规则 `/dev/input/event11` 仍是 `root:input 0660`；`udevadm test` 显示 `TAGS=:power-switch:`，无 `uaccess`。
- **原因**：蓝牙 HID 的父设备是虚拟设备 `/sys/devices/virtual/misc/uhid/0005:2717:32B8.xxxx`，**没有 `idVendor`/`idProduct` 属性**（只有 uevent 里的 `HID_ID`）；且文件名 `99-` 排在系统 `73-seat-late.rules` 之后，即使打了 `uaccess` 标签也不会触发 ACL 内置动作。
- **解决**：按设备名匹配（`ATTRS{name}=="小米蓝牙语音遥控器"`），文件名改 `70-` 前置到 73 号之前。验证 `TAGS=:power-switch:uaccess:seat:` 且出现 `user:chenwei:rw-`。

#### 2.6.2 坑 2：官方安装器装完命令无法执行

- **现象**：提示"安装完成"，但 `mi-remote` 报 `无法执行：找不到需要的文件`。
- **原因**：安装器 `mkdtemp` 建临时 venv → 改名；venv 脚本 shebang 写死临时路径（`.../versions/.0.4.1.install-xxxx/bin/python3`），改名后失效。
- **解决**：批量改写 shebang（命令见 2.3.3）。

#### 2.6.3 坑 3：两台遥控器都在配对状态，自动识别有歧义

- **现象**：旧遥控器（无 TV 键）与新遥控器都是 `VID:PID 2717:32b8` 且都显示已连接。
- **解决**：服务与调试命令都用 `--address <MAC>` 锁定；确认活动设备看 `HID_UNIQ`：

```bash
grep HID_UNIQ /sys/devices/virtual/misc/uhid/0005:2717:32B8.*/uevent
```

#### 2.6.4 坑 4：下载速度的误判

- 清华 PyPI 镜像实测只有 **0.23～1.2 MB/s**，一度以为要绕道海外服务器。
- 但 **HuggingFace 直连 9.7 MB/s**（hf-mirror 10.0），233 MB 模型 **21.7 秒**下完。
- 结论：不同源差别极大，**先测速再决定要不要绕路**。

#### 2.6.5 坑 5：`test keys` 是严格按顺序的

13 个键必须按指定顺序按；按错会被记为"意外按键"并继续等，超时即失败并中断后续。想快速确认有哪些键/码值，用 `mi-remote keys watch`（无顺序要求）。

#### 2.6.6 坑 6：GNOME Wayland 下所有按键注入都失效（最关键）

- **现象**：按遥控器键弹出 `/usr/bin/wtype exited with 1: Compositor does not support the virtual keyboard protocol`；以及 `xdotool ... XGetWindowProperty[_NET_ACTIVE_WINDOW] failed`。
- **原因**：
  1. Mutter **不实现** wtype 依赖的 `zwp_virtual_keyboard` 协议（`doctor` 只查命令是否存在，会误报"✓ 虚拟按键"）。
  2. xdotool 只支持 X11。
  3. 项目在 wayland 分支**优先用 wtype**，运行时失败**不会自动回退**。
- **解决**（四步缺一不可）：
  1. `sudo apt remove wtype`；
  2. **自写 uinput 垫片**（Ubuntu 的 ydotool 包缺 `ydotoold`，上游依赖仓库已失效）；
  3. **常驻**（2.1 秒/次 → 30 ms/次）；
  4. 服务里把 `~/.local/bin` 前置到 PATH，否则 `which("ydotool")` 命中 `/usr/bin/ydotool`（连不上）。

#### 2.6.7 坑 7：终端里语音粘贴无效

- **原因**：Wayland 下无法识别当前窗口是否终端，`--paste-shortcut auto` 回退成 `Ctrl+V`，而终端粘贴是 `Ctrl+Shift+V`；OpenCode 跑在终端里，所以粘不进去。
- **解决**：服务加 `--paste-shortcut ctrl-shift-v`。

#### 2.6.8 坑 8：垫片自动拉起守护进程时解释器不对

- **原因**：默认 `python3` 是 conda 的（无 `evdev`），靠 shebang 拉起会崩。
- **解决**：垫片自动挑选带 `evdev` 的解释器（优先 mi-remote 的 venv，支持版本目录变化）；systemd 单元也显式用 venv python。

#### 2.6.9 坑 9：基础层「长按返回」是硬编码的（曾打补丁，现已回退）

- **现象**：配置里 `back.hold` 怎么写都不生效，日志写 `hold back (protected base delete)`。
- **原因**：`_hold_timer` 对 `key == "back" and effective_layer == 0` 硬编码"只发一次 Backspace"（防误触清空输入）。
- **解决**（两步）：
  1. 打补丁，改成"配置里显式写了 `hold` 就尊重配置"：
     `if key == "back" and self.effective_layer == 0 and self._binding(key).hold is None:`
     （`system/patch/` 里有原始文件、补丁后文件和一键重打脚本）
  2. `back.hold` 改成连删脚本 `backspace-burst 1.2`：把 Backspace **按住 1.2 秒不放**，借系统按键自动重复连删（真机实测删 26 个字符）。
  3. `Esc` 放在**双击**上（双击不受任何分支影响）。

| 操作 | 实际发出 | 效果 |
|---|---|---|
| 单击 | `Backspace` | 301 ms（等 `double_ms` 250ms 后）→ 删一个字符 |
| 双击 | **`Esc`** | 171 ms |
| 长按 | **`backspace-burst 1.2`** | 352 ms 触发 → 连删约 26 个字符 |

- **代价**：单击被 `double_ms` 推迟；连删量是**固定**的（脚本时长决定，不是"按住多久删多少"——单键设备收不到松手事件）。
- 验证：`tests/test_double.py`（行为仿真）+ 测试终端 readline 实测连删量。
- **【已回退 2026-10-06】**：评估后确定不做长按连删（改为逐次短按删除）→ `back.hold` 已删除、本机补丁已还原（`mapping_engine.py` 回到原版）。当时返回键：短按 = 删除（即时）、长按 = 删一个、双击已移除；`Esc` 改由**电源短按**触发。
- **【已重新启用 2026-10-08】**：按需求恢复「长按 = 连续快删」。脚本从 `extras/` 提回 **`scripts/backspace-burst`**（`install.sh` 会装进 `~/.local/bin`），`system/mapping.json` 的 `back.hold` 指向它（`backspace-burst 1.2`），并重新应用本机 mapping 补丁：`bash system/patch/apply-patch.sh --mapping`。
  > ⚠️ **mapping 补丁改的是本机 venv 里的 `mapping_engine.py`，不是仓库文件** —— 重装/升级 mi-remote 后必须重跑，否则「长按返回」又会退回"只删一个"。

#### 2.6.10 坑 10：GNOME Wayland 下没法把已有窗口拉到前台

- **需求**：双击主页/TV 打开程序时，如果该目录已开着，应该**切到那个窗口**。
- **为什么难**：Wayland 不允许后台进程激活别人的窗口。
  - `xdotool`/`wmctrl` 只认 X11，本机没有可用的 XWayland 窗口
  - `org.gnome.Shell.Eval` 被禁用（AccessDenied）
  - gnome-terminal 的窗口由 `gnome-terminal-server` 创建，客户端设 `GDK_BACKEND=x11` 无效
  - 也没装 Window Calls 之类提供 Activate API 的扩展
- **解决**：本机**已有** CUA 的 GNOME 扩展 **`winrects@cua`**（原本未启用），DBus 暴露：
  - `GetRects()` → 所有窗口的 `id/pid/title/x/y/w/h/focused`
  - `Activate(id)` → 激活窗口（实测返回 `true` 且窗口切到前台）
  - 启用：`gnome-extensions enable winrects@cua`
- **实现**：`window-find-focus` 助手 + 启动器；Cursor 按标题 `" - <目录名> - Cursor"` 匹配；OpenCode 的标题会被改成 `OC | 会话名`，改用 `~/.local/state/mi-remote/opencode-window-<目录哈希>.id` 记窗口 id（首次启动时后台 diff 得到）。
- **降级**：扩展不可用 → 启动器直接新开窗口，不影响使用。
- **附带**：`cua-driver` 的 `bring_to_front` 也能做，但需要常驻守护进程；直接调扩展更轻，故未依赖它。

#### 2.6.11 坑 11：Alt+Tab 只能切两个窗口（MRU 陷阱）

- **现象**：把 `Alt+Tab` 绑到"长按菜单"，实测焦点只在最近两个窗口间来回跳。
- **原因**：GNOME 每次**独立**按下 `Alt+Tab`（含松开）都会把当前窗口提到 MRU 首位，于是下一次又切回上一个。
- **解决**：实现**保持 Alt** 的窗口切换器 —— 先 `Alt↓ + Tab` 弹出切换器，再由 ←/→（或再次长按菜单）移动选择，最后松开 Alt 完成选定。
  - 用 `winrects@cua` 的 `focused` 字段做**客观验证**：无方向键 / 一次 → / 两次 → 三种情况提交的窗口都不同 ✅
  - 计时用"**闲置 8 秒**"（不是固定 8 秒），每次再长按菜单都顺延，避免手慢就错过
  - Alt 一定会释放：正常超时收尾 + 脚本 `trap` 兜底
- **附带发现**：切换器弹出后按 `Esc` 可取消（焦点不变）。

#### 2.6.12 坑 12：重启后遥控器整只失效（HID 节点没挂上）

- **现象**：电脑重启后，`mi-remote.service` 与 `mi-remote-uinputd.service` 都 `active`、托盘进程也在，`bluetoothctl info` 显示遥控器
  `Connected: yes`，但**按键和语音全都没反应**；`mi-remote doctor` 报 `✗ 遥控器按键输入: 未发现 RC003 evdev 节点`，托盘是 🔴/🟡。
- **根因**：BlueZ 的 **HID-over-GATT（HOG）** 通道偶尔没建起来。实测此时遥控器**确实连着**，GATT 里也**确实有 HID 服务**：

  ```bash
  # 设备对象下有 00001812（HID）服务 → 遥控器没坏，是 BlueZ 没把它接成输入设备
  busctl --system tree org.bluez | grep -o 'service[0-9a-f]*' | ...
  # 关键：/sys/devices/virtual/misc/uhid/ 下没有 0005:2717:32B8.*
  ```

  进而按键没有 `/dev/input/eventN` 可读、ATVV 语音也收不到通知。日志里伴生
  `hci0: Opcode 0x200e failed: -16`、`device_set_wake_support() Unable to set wake_support without RPA resolution`、
  `No matching connection for device`。**不是**遥控器休眠（休眠时 `Connected: no`），也**不是**节点权限问题。
- **关键结论**：只做「断开重连」**清不掉**（实测停服务 + 断开 + 重连后，60 秒内 HOG 仍不出现）。能清掉的两种手法：
  1. `bluetoothctl block <MAC>` → `unblock`（强制 BlueZ 丢掉旧链路**新建**连接）；
  2. `systemctl restart bluetooth`（最后手段；需 polkit 授权，登录会话内可无密码执行）。
- **解决**：新增自愈脚本 `scripts/baton-bt-recover`（装到 `~/.local/bin/`），按 **轻 → 重** 逐级恢复并每级复检按键节点：
  1. 先等 8 秒（正常晚挂载）；
  2. 蓝牙未连接 → 判定为遥控器休眠，**不做任何破坏性操作**，提示按任意键唤醒；
  3. 已连接却无节点 → 轻量重连 → `block/unblock` → 重启 `bluetooth.service`。
- **接线**：托盘菜单「重连蓝牙（自愈）」改为调用该脚本；并新增用户服务 `baton-recover.service`
  （`After=graphical-session.target mi-remote.service`，登录后 `sleep 6` 再自愈一次），随 `install.sh` 安装并 `enable`。
  这样**重启后开箱即恢复**，无需手点。
- **验证**：`baton-bt-recover --check`（退出码 0=正常）；脚本正常输出 `✅ 按键节点已恢复：/dev/input/eventN`。

#### 2.6.13 坑 13：遥控器睡着后不会自己连回来

- **现象**：用着用着遥控器没反应了；`bluetoothctl info` 显示 `Connected: no`，`mi-remote` 日志每 1~15 秒
  `连接失败: BLE 连接超时（10.0s）`，一直连不上，直到手动重启蓝牙栈才好。
- **排查（关键事实）**：
  1. 遥控器"睡着"时**仍在广播** —— `bluetoothctl info` 的 `RSSI` 一直有值（实测 -68 左右）。
     所以不是它不可达。
  2. BlueZ 5.72 默认 `ReconnectUUIDs` 里**没有 HID（`00001812`）**，链路丢失后 BlueZ 不会主动把
     遥控器连回来（`/etc/bluetooth/main.conf` 的 `[Policy]` 段）。
  3. `mi-remote` 每次连接超时都会在 BlueZ 里留下一个**挂起的连接请求**，之后所有连接尝试都被
     `Operation already in progress` 挡住 —— 这才是"一直连不上"的直接原因。
- **实测**：停掉 `mi-remote` 后单独 `bluetoothctl connect` 仍被挂起挡住；而
  **`bluetoothctl disconnect`（取消挂起）→ `connect`** 一次就连上；`systemctl restart bluetooth`
  后 `connect` 也必然成功（但会短暂影响其它蓝牙设备）。
- **解决**：新增常驻看门狗 `scripts/baton-bt-watchdog`（`system/baton-bt-watchdog.service`，随
  `install.sh` 安装并 `enable`）：
  - 平时只体检（每 8 秒看"已连接且 HID 按键节点在"），**不打扰** `mi-remote`；
  - 掉线后先给 `mi-remote` **20 秒宽限**（它多数情况能自己连回）；
  - 仍掉线才出手：试连 → 若 BlueZ 报 `already in progress` 就 **`disconnect` 清掉挂起再连**
    （挂起在 BlueZ 里，停 `mi-remote` 也清不掉，所以**不暂停服务**）；
  - 没连上按 **15s → 最多 60s** 退避安静等待（遥控器深度休眠时谁连都没用）。
  - **默认不重启蓝牙栈**：它要 polkit 授权（会弹密码框），且实测遥控器深度休眠
    （连广播都停）时重启也没用，纯属白重启。需要时才设 `BATON_WD_ALLOW_RESTART=1`。
- **免密码重启蓝牙**（可选兜底用）：`system/49-baton-bluetooth.rules` 随 `install.sh` 装到
  `/etc/polkit-1/rules.d/`，只放开"本地会话活动用户启停/重启 `bluetooth.service`"，不存密码
  （公开仓库安全）。装后非 root 执行 `systemctl restart bluetooth` 不再弹密码。
- **验证**：停掉 `mi-remote`、人为 `bluetoothctl disconnect` 断开后，看门狗在**几秒内自动连回**，
  `ls /sys/devices/virtual/misc/uhid/` 出现 `0005:2717:32B8.*`，`mi-remote doctor` 恢复正常。
- **手动排障**：`baton-bt-watchdog --once` 跑一轮宽限+恢复。
- **注**：若遥控器**关机 / 没电 / 被别的主机占用**，它连广播都不会发（`bluetoothctl info`
  里连 `RSSI` 都没有），此时任何软件都连不上，需先唤醒/换电池/断开别的主机。

#### 2.6.14 坑 14：语音识别越来越不准（音频通知被重复订阅）

- **现象**：语音识别从「偶发乱码」一路恶化到「几乎全错」，而且**同一个进程跑得越久越糟**；
  重启 `mi-remote.service` 后立刻恢复正常。曾误判为「遥控器没电」（实测电量 85%，无关）。
- **排查（关键事实）**：日志里每次录音有一对 `音频流开始` / `音频流结束`，可据此算
  **解码时长 ÷ 实际按键时长**：
  | 进程内每次会话的「音频流开始」次数 | 解码/实际倍数 | 实际结果 |
  |---|---|---|
  | 1 | 0.93–0.99（正常） | 识别正确 |
  | 2 | 1.96 | 开始变差 |
  | 3 | 2.97 | 更差 |
  | 4–5 | 4.4–4.9 | 几乎全错 |
- **根因**：`mi-remote` 每经历一次 BLE 重连，音频 notify 就**多出一层订阅**；同一帧音频被解码
  **N 次**，喂给云端 ASR 的 PCM 被拉长为实际录音的 N 倍。ADPCM 解码器被喂重复字节后预测器
  「顶轨」，波形变成 `峰值 32768` + 大直流偏置（实测 +6000 上下）+ 低频能量占 66% 以上
  —— 这正好解释了历史日志里「削波乱码」的假象（早期被当成"遥控麦太热"，见 `--gain 0` 那条）。
  倍数随进程存活期间的重连次数**累积增长**（本机实测从 0.93 一路涨到 4.88）。
- **为什么难发现**：`ble_client.py` 有 `generation` 守卫，理论上应该拦住过期回调，但实测没拦住；
  根因在 bleak/BlueZ 的 watcher 生命周期（同一 device 的 `StartNotify` 订阅会累积），
  具体层级未完全定论（见「还能怎么继续玩」）。
- **解决（当前）**：新增常驻守卫 `scripts/baton-asr-guard`（`system/baton-asr-guard.service`，
  随 `install.sh` 安装并 `enable`）：
  - 判据：**一次录音会话里「音频流开始」> 1 次**（正常恰好 1 次）—— 这是最可靠的指纹；
  - 只增量读新增日志（游标文件 `~/.local/state/baton-asr-guard.cursor`），命中即
    `systemctl --user restart mi-remote.service`，重启后订阅回到 1；
  - 重启后静默冷却（默认 300s）避免抖动风暴；平时完全不动作，也不碰蓝牙链路。
- **验证**：把游标拨回那次坏会话（`「音频流开始」5 次`）跑 `baton-asr-guard --once`，
  守卫正确检出并重启，`mi-remote` 几秒内恢复 `active`；正常会话（1 次）不误报。
- **手动排障**：`baton-asr-guard --once`（0=健康 / 1=刚自愈 / 2=读取失败）。
- **立即止血**：任何时候觉得识别不对劲，`systemctl --user restart mi-remote` 即可恢复到 1×。

### 2.8 还能怎么继续玩（可选）

- **改键**：编辑 `mapping.json` → `validate` → 重启（1.9 有写法示例）

- **把 OpenCode 动作绑成独立按键**：改 `tui.json`，避免与终端快捷键冲突
- **恢复已撤功能**：鼠标模式 `power.hold`、OpenCode 层（用备份配置）、音量键（`system: volume_up`）
- **硬件改造**：改锂电池 + Type-C 充电（TP4056）；拆机把按键接 ESP32 刷 ZMK/QMK 做通用 BLE 遥控器
- **红外款补救**：加 USB 红外接收头 + `ir-keytable` 自行录码建 keymap
- **根治坑 14 的根因（可选）**：`ble_client.py` 里有 `generation` 守卫，理论上应拦住过期的 notify 回调，但实测没拦住 —— 需要进一步定位 bleak / BlueZ 的 watcher 生命周期为何让 `StartNotify` 订阅逐次累积。定位后可去掉常驻守卫 `baton-asr-guard`
- **HDMI-CEC**：本机 AMD 核显驱动未实现 CEC 适配器（无 `/dev/cec`），要走这条路需外接 USB-CEC 适配器
